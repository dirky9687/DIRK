# DIRK v0.7.19 - Red + Bluetooth Assessment Pass (SOURCE TEST)

Built from v0.7.18 FIX1. Code is not compiled with PlatformIO or tested on a Cardputer ADV in this environment. Keep v0.7.18 FIX1 as the firmware fallback.

## New Red Team feature: dual-band policy review
- Red Operations > Dual-Band Policy Review: inspect saved AND authorized AP observations, separated by BSSID.
- Requires exact non-placeholder SSID matching on 2.4 GHz and 5 GHz to show paired observations. A matching SSID does not prove AP equivalence.
- Reports WPS advertisement/PMF details for the S3 2.4 GHz radio, warns that C5 5 GHz RSN details are coarse/unknown.
- Up/Down selects the authorized observation; Left/Right changes finding page; Tab exports a CSV under /dirk/reports/dual_policy_<BSSID>.csv.
- No new RF packets, scan commands, authentication attempts, or radio injections.

## Bluetooth expansion
- Bluetooth > Authorized Lab is now a live read-only BLE advertisement inventory with selection, rather than a placeholder.
- Up/Down choose a recently scanned device; Tab requests an async BLE scan if the S3 Wi-Fi scanner and Wardrive are idle; Enter snapshots the selected device.
- On the BLE assessment page: Left/Right browse findings; Tab once requests explicit owned-device confirmation; Tab again exports the report under /dirk/reports/ble_posture_<address>.csv.
- Findings include name exposure, iBeacon/Eddystone advertisement, mesh signatures, manufacturer metadata, service UUID and advertised TX power. Does not capture raw manufacturer payload in CSV.
- Added bounded manufacturer-data and service-data lengths to the BLE provider. This is advertisement parsing only, not GATT service enumeration.
- Only review/export an owned or expressly authorized device. Advertising addresses can be randomized, so name or address is not a verified device identity.
- No BLE connections, characteristics reads/writes, pairing, flooding, or stress tests.

## Red tool result clarity
- Management-frame test results now distinguish a radio TX-request outcome from an observed client/AP effect. A successful transmission return is not evidence of disconnection or PMF failure.

## Device validation
1. Build with `pio run -e cardputer-adv`; flash via SD/M5Launcher. Verify boot/version and navigation.
2. Confirm combined AP scanner shows known 2.4+5 GHz networks, then Wardrive GPS/5 GHz/BLE and smooth Buddy menu exit.
3. Save and authorize BOTH radios of your own dual-band SSID; open Red > Dual-Band Policy Review; confirm pairing and findings.
4. Check 5 GHz details never invent WPS/PMF and that an unpaired SSID is reported UNKNOWN.
5. Insert writable SD; Tab exports /dirk/reports/dual_policy_*.csv.
6. BLE > Authorized Lab; Tab to scan, choose your BLE test device, Enter for assessment; Left/Right finding pages.
7. Tab once should request confirmation; only second Tab writes /dirk/reports/ble_posture_*.csv. Confirm report contents and no unrelated device details collected.
8. Test Back from both new detail screens, rapid menu changes, and no text below y=116. With Wardrive running, BLE lab scan should not interrupt it.
9. Verify deauth/disassoc statuses do not claim client behavior based on a raw TX return alone.

## Known limits
- The ESP32-S3 cannot do 5 GHz packet injection/monitor-mode capture. No 5 GHz active RF support implied.
- BLE is passive advertisement assessment. GATT permissions, authentication, pairing security and active BLE vulnerabilities are untested.
- Local file evidence contains observed MAC/SSID/address details; handle exported reports with care.
- Native C++ and static source regressions are not an embedded firmware compilation. Confirm on Kali/Cardputer before treating as stable.
